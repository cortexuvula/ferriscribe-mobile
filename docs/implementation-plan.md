# FerriScribe Mobile — Implementation Plan

## Phase 0 — Scaffold & pairing (P0)

- Flutter project init (iOS + Android), Tailscale reachability to the server (probe `GET :11436/info`).
- `flutter_secure_storage` for the bearer token; `sqlcipher_flutter_libs` (pin `^2.1.0`) + `drift` for the local document cache.
- Android `FLAG_SECURE` + iOS screen-capture protection + **app-switcher snapshot masking** (blur overlay on `AppLifecycleState.inactive`).
- **Backup exclusion:** iOS `NSURLIsExcludedFromBackupKey` on the app data dir; Android `android:allowBackup="false"` + extraction rules.
- Pairing flow: QR (the desktop QR carries `pp=11436` + `vp=11437` + Tailnet host) → `POST /pair/enroll` → long-lived bearer token persisted in the secure store. No refresh flow exists server-side; do not invent one.
- No Sentry/Crashlytics/Firebase integrated.

**Acceptance:** app pairs to a running office-server; token persists securely across restarts; `GET :11436/info` probe succeeds over Tailscale; app-switcher shows blur not content; backup excludes app data.

## Phase 1 — Record + ingest (P1) ⚠️ depends on the server-side track

> **Critical path dependency:** the server track must deliver recording ingestion (`POST /v1/recordings` or metadata-push + `PUT /v1/content/audio/{id}`) and job status (`GET /v1/jobs/{recording_id}`) before this phase can be verified end-to-end.

- Microphone capture (`record` **streaming API`) multiplexed **directly into the upload request** — no plaintext audio file ever lands on disk (the `record` package's default temp-file path is a local at-rest PHI leak: recoverable from unallocated blocks even after deletion — independent of transport security). **No client-side encryption** — audio is uploaded as plaintext bytes; the server encrypts at rest (FE1) on receipt. Where a platform technically forces a temp file: app-private storage only, and it is **shredded (overwritten, not merely deleted) immediately after upload confirmation**.
- Upload + trigger `process_recording` (server-side transcribe → SOAP), then job-status SSE (`GET /v1/jobs/{recording_id}`).
- Progress model (verified from source): `transcribing → generating_soap → completed | failed` for the base pipeline; referral/letter/synopsis/peer-discussion are separate server commands triggered individually (`POST /v1/recordings/{id}/generate/{doc_type}`).
- SSE handling: manual line-splitting with reconnect logic, or the `sse_client` package. The server already runs SSE on :11437 (`/v1/content/events`, `/v1/user-dictionary/events`, `/v1/condition-chips/events`) — follow those patterns.
- SSE constraint: event payloads carry IDs only, no PHI.

**Acceptance:** record a consultation on the phone → a SOAP note appears, generated by the local server. Temp-dir scan after the recording session shows zero plaintext audio files (any platform-forced temp file is verified shredded — overwritten, not merely deleted — immediately after upload).

## Phase 2 — Five doc types + review/edit

- Fetch documents via `/v1/content/sync` pull (fields: transcript, soap_note, referral, letter, peer_discussion — synopsis is **not** a synced field; fetch on demand once the server exposes it).
- Trigger generation per doc type (`POST /v1/recordings/{id}/generate/{doc_type}`).
- Editors for `soap | referral | letter | synopsis | peer_discussion`; save edits back via content-sync push or the net-new document PUT.
- Clipboard: explicit user-initiated copies only, never auto-copy.

**Acceptance:** view and edit all 5 doc types on-device; edits persist to the server.

## Phase 3 — Export + share

- Export via `GET /v1/recordings/{id}/export?format=pdf|docx&doc_type=…` (server invokes `medical-export`; **synopsis + peer_discussion exporter paths are net-new server work** — existing exporters cover soap/referral/letter only).
- System share sheet for the resulting PDF/DOCX.

**Acceptance:** export a SOAP note to PDF and share it from the phone; synopsis + peer_discussion exports work once the server track lands them.

## Phase 4 — Offline + polish

- Offline read cache (SQLCipher) of fetched documents.
- Patient context capture; error/retry UX; empty/loading states.
- Unpair flow (self-revocation endpoint from the server track, or instruct desktop-side revoke via `POST /pair/revoke/:id`).

**Acceptance:** previously fetched documents are viewable with the server unreachable.

## Parallel track — server-side (CRITICAL PATH, mostly net-new)

The server delta is **mostly net-new**, not an extension of `medical-sharing`'s pairing API. What exists and is reusable: pairing (`/pair/enroll`), the :11437 data API scaffolding (axum router, bearer auth via `TokenStore`, SSE infrastructure, `PUT /v1/content/audio/{id}` plaintext-audio ingestion with server-side FE1 at-rest encryption), and all generation commands. What is missing is everything job-shaped and mobile-shaped:

1. **Recording ingestion** — `POST /v1/recordings` (or metadata push via content sync + existing audio PUT); enqueue processing.
2. **Job queue + status over HTTP** — greenfield. `queue_tasks`/`ProcessingEvent` types exist in `medical-core` but no HTTP surface; `process_recording` reports progress only as in-process Tauri events. Need `GET /v1/jobs/{recording_id}` (status + SSE) mapping to real stages: `transcribing → generating_soap → … → completed|failed`, plus per-doc-type generation commands.
3. **Generation triggers** — HTTP wrappers over the existing `generate_referral/letter/synopsis/peer_discussion` commands.
4. **Document read/write** — `/v1/content/sync` already covers transcript/soap/referral/letter/peer_discussion per-field LWW; add synopsis handling (no dedicated column today — stored in recording metadata) and/or a mobile-friendly document GET/PUT.
5. **Export endpoints** — stream `medical-export` output; add synopsis + peer_discussion exporters (generic `render_document` can carry them).
6. **Self-revocation** — `POST /pair/revoke/:id` is loopback-gated; add a non-loopback self-revocation path or document desktop-side revocation as the answer.

Reuse the existing pipelines, providers, and `medical-export` crate. No new inference code.

SSE constraint: event payloads carry IDs only — no patient names or transcript content.
